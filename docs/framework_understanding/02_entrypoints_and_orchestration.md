# Phase 2 - Entrypoints and Orchestration

## Primary entrypoint

`spec2testbench/presentation/cli/main.py` is the main user entrypoint.

### `verify`

- Arguments:
  - `--specs/-s`
  - `--netlist/-n`
  - `--output/-o`
  - `--format/-f`
  - `--provider/-p`
  - `--no-llm`
  - `--verbose/-v`
- Files loaded:
  - YAML spec file via `Specification.from_yaml()`
  - optional netlist path
  - environment-backed settings from `spec2testbench/config/settings.py`
- Objects created:
  - optional `LLMClient`
  - `VerificationPipeline`
  - `VerificationReport`
  - `ReportFormatter`
- Statuses produced:
  - `ExecutionStatus`, `SimulationMode`, `ComplianceStatus`, `RobustnessStatus`, `ScientificCategory`, `ValidationStatus`
- Files generated:
  - markdown or json report in configured report directory

### `generate`

- Loads spec YAML.
- Builds optional `LLMClient`.
- Instantiates `VerificationPipeline`.
- Calls `pipeline.testbench_gen.generate(specification)`.
- Outputs generated PySpice code when `--output` is provided.

### `diagnose`

- Loads waveform PNG and optional spec YAML.
- Requires configured LLM provider.
- Instantiates `WaveformChecker`.
- Produces multimodal diagnostic result, optionally markdown output.

### `draw`

- Loads SPICE netlist text.
- Calls schematic infrastructure.
- Produces SVG/PDF/PNG plus connectivity evidence JSON.

## Real orchestration center

Fact observed:
- The real verification orchestration is not in CLI code; it is in `spec2testbench/application/usecases/run_verification.py`, class `VerificationPipeline`.

### `VerificationPipeline.verify()`

High-level ordered steps:

1. generate testbench with `self.testbench_gen.generate(specification)`
2. attach metadata and optional netlist path to the generated `TestBench`
3. run real simulation when a netlist path exists
4. otherwise use mock simulation only if explicitly allowed
5. parse execution and simulation mode statuses
6. merge authoritative native backend metrics if present
7. validate whether required metrics/analyses/units are even evaluable
8. run `SpecChecker.verify()` if execution succeeded and prechecks passed
9. run optional waveform diagnosis for failed metrics
10. derive final statuses and paper-eligibility
11. build provenance payload

## Text call graph

```text
CLI verify()
  -> VerificationPipeline(...)
  -> VerificationPipeline.verify_from_yaml(spec_path, netlist_path)
      -> Specification.from_yaml(spec_path)
      -> VerificationPipeline.verify(specification, netlist_path, spec_path=spec_path)
          -> TestBenchGenerator.generate(specification)
              -> _determine_categories()
              -> generate_for_category(...)
                  -> _generate_with_templates(...) or _generate_with_llm(...)
              -> _merge_testbenches(...)
          -> _run_simulation_with_ngspice(netlist_path, testbench)
              -> PySpiceSimulator.run(netlist_path, testbench)
          -> _validate_required_metrics(...)
          -> SpecChecker.verify(simulation_results, specification)
              -> extract_metrics(...)
                  -> MetricExtractor.extract(...)
              -> verify_single_metric(...)
          -> _finalize_report_statuses(...)
          -> _build_provenance(...)
      -> ReportFormatter.to_markdown(...) or to_json(...)
```

## Script orchestration

### `scripts/run_paper_campaign.py`

Observed flow:

1. discover specs in `examples/benchmark_specs/`
2. pair them with netlists in `benchmark/analogcoder_pro/`
3. instantiate `VerificationPipeline(use_llm=False, allow_mock=False, allow_recovery=True, timeout_seconds=60)`
4. call `verify_from_yaml()` for each case
5. write copied spec/netlist, generated `testbench.cir`, `metrics.json`, `provenance.json`, markdown/json reports
6. aggregate CSV/JSON campaign summaries

Important consequence:
- the canonical paper campaign uses the deterministic path, not the LLM generation path.

## Architectural reading

Fact observed:
- orchestration is centralized in one use-case class and reused by CLI, scripts, and tests.

Interpretation:
- this is the closest thing to an application service layer in the repository.
