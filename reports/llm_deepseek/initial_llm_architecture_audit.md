# Initial LLM Architecture Audit

Date: 2026-07-21

## Scope

Audit performed before implementation of the new DeepSeek experimental branch.

Protected area status at audit start:

- `git diff -- paper_final/` was empty.
- Existing uncommitted changes were present outside `paper_final/`; they were not modified by this audit.

## Existing LLM Interfaces

Primary text client:

- `spec2testbench/infrastructure/llm/llm_client.py`
- Single concrete `LLMClient` with embedded provider branching.
- No provider-agnostic application port.
- Domain and application layers currently depend on infrastructure-level client shape indirectly through constructors.

Current planner-oriented LLM path:

- `spec2testbench/infrastructure/testbench/llm_guided_synthesis.py`
- Defines ad hoc dataclasses:
  - `TestbenchPlan`
  - `MeasurementPlan`
  - `SourceAction`
  - `AnalysisAction`
- These are not the requested scientific `TestbenchPlan` schema.
- Current planner can operate deterministically or via LLM and writes plan metadata into `TestBench.metadata["llm_guided_plan"]`.

CLI entrypoints touching LLM:

- `spec2testbench/presentation/cli/main.py`
- Supports provider selection and optional planner LLM mode.

Campaign/helper script using LLM:

- `scripts/run_llm_mode_comparison.py`
- Compares deterministic vs current LLM-assisted generation, but does not implement the requested DeepSeek-only scientific protocol.

## Existing Providers

Implemented in `spec2testbench/infrastructure/llm/llm_client.py`:

- OpenAI
- DeepSeek via OpenAI-compatible endpoint
- Groq via OpenAI-compatible endpoint
- Gemini
- Anthropic

Observations:

- Provider selection is embedded in one class.
- No `Protocol`/port for provider swapping at the application boundary.
- No dedicated DeepSeek provider module.
- DeepSeek base URL is hardcoded as `https://api.deepseek.com/v1`, not externally controlled through `DEEPSEEK_BASE_URL`.

## Existing Prompts

Current testbench prompts:

- `spec2testbench/infrastructure/testbench/prompts/testbench_prompts.py`
- Category-specific prompt generation for `dc`, `ac`, `transient`, `spectral`, `pvt`, `differential`
- Output format is a generic JSON testbench description with stimuli, analyses, and measurements.

Current planner system prompt:

- Embedded string in `LLMGuidedPlanner.SYSTEM_PROMPT`
- Instructs the model to return structured JSON and avoid duplicate sources.
- Not versioned on disk.
- Not aligned with the requested constrained DeepSeek planning prompt.
- Does not explicitly include the final scientific leakage prohibitions requested for this mission.

Waveform multimodal prompts/clients also exist separately, but they target image analysis rather than testbench planning:

- `spec2testbench/infrastructure/waveform_checker/llm_multimodal_client.py`
- `tests/test_multimodal_client.py`

## Existing Output Formats

Current text generation output:

- Raw string returned from `LLMClient.complete(...)`
- Optional JSON mode requested through `response_format={"type": "json_object"}` for OpenAI-compatible providers.

Current structured planner output:

- Parsed into ad hoc dataclasses in `llm_guided_synthesis.py`
- Stored in `TestBench.metadata["llm_guided_plan"]`

Current framework execution artifacts:

- Generated by `VerificationPipeline` and `PySpiceSimulator`
- Already include provenance, hashes, native backend results, measurement backend information, and ngspice metadata

Gap:

- No dedicated artifact tree for LLM planning request/response provenance per case/trial/mode.

## Existing Validation Mechanisms

Specification and pipeline validation:

- `Specification.validate()`
- `TestBench.validate()`
- `VerificationPipeline._validate_required_metrics(...)`
- `MetricExtractor.supports_metric(...)`
- Existing netlist binding hash checks in `PySpiceSimulator`
- Existing native backend handling for `NGSPICE_MEASURE` and `NGSPICE_WRDATA`

Current planner validation:

- `TestbenchPlanValidator` in `llm_guided_synthesis.py`
- Checks duplicate driven nodes, known nodes, supported analyses, and presence of matching analysis actions
- Does not validate:
  - schema with strict enums
  - case/spec/netlist hash identity
  - unit compatibility against a metric registry
  - verdict leakage
  - simulation cost bounds
  - backend support contract per metric
  - requested-vs-extra metric exactness at the required scientific level

## Existing Retry Mechanisms

No provider-level retry layer was found for text LLM generation.

Current status:

- `LLMClient.complete(...)` delegates directly to SDK calls
- No bounded exponential backoff
- No HTTP status classification
- No structured per-attempt logging
- No explicit truncated-response classification

## Existing Cache

No reproducible LLM cache was found for testbench planning.

Findings:

- `scripts/run_llm_mode_comparison.py` performs direct calls
- No cache key including prompt/spec/netlist/provider/model hashes
- No `--resume` / `--force-new-llm-call` semantics for LLM planning

## Obsolete or Scientifically Risky Code Paths

For the requested DeepSeek evidence branch, the following are insufficient or risky if reused directly without isolation:

- `LLMClient` as the only interface
  - mixes providers
  - has no retry policy
  - no typed response metadata object
- `LLMGuidedPlanner`
  - schema does not match requested `TestbenchPlan`
  - prompt is embedded and not versioned
  - no scientific leakage guardrail set matching the mission
- generic category prompt generation in `testbench_prompts.py`
  - useful conceptually, but not adequate for the requested one-object constrained planner protocol
- `scripts/run_llm_mode_comparison.py`
  - compares broad modes but lacks artifact provenance, repair loop accounting, cache, and campaign protocol requested here

## Risks To The Deterministic Pipeline

Main risks if the new branch is not isolated:

- accidental regression of the deterministic D0 path in `TestBenchGenerator`
- contamination of final verdict logic by LLM-originated outputs
- exposure of ground-truth labels or historical verdicts in prompts or artifacts
- silent fallback from real ngspice/native backends to mock behavior
- metric alias normalization collapsing distinct requested metrics
- provider/network failures being misclassified as circuit/testbench failures
- mixing free-form SPICE generation with validated deterministic compilation

## Audit Conclusion

The repository already contains:

- a usable deterministic verification core,
- an existing multi-provider LLM client,
- native ngspice result backends,
- early LLM-guided planning scaffolding.

However, it does not yet contain the provider-agnostic, DeepSeek-specific, scientifically isolated planning pipeline requested for this mission.

Recommended implementation direction:

1. Add a new application-level LLM provider port and typed request/response objects.
2. Add a dedicated DeepSeek provider with explicit retries, error taxonomy, timeout handling, and model discovery.
3. Introduce a strict Pydantic `TestbenchPlan` schema separate from the existing ad hoc planner schema.
4. Build a separate capability export, semantic validator, deterministic compiler, and campaign runner under `llm_deepseek`.
5. Reuse the existing deterministic simulator/checker path only after validated plan compilation, preserving D0 unchanged.
